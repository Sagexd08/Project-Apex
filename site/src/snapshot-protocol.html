Why a log position is not a snapshot

A sequence number says how far the log has grown. A snapshot says which immutable index state a reader may use. They are only the same thing if the system defines, and checks, the relationship between committed writes, applied index state, published segments, deletions and reclamation. Established systems keep that relationship explicit: RocksDB snapshots are sequence numbers pinned against compaction, SQLite readers record a WAL end mark, and RCU readers hold an epoch.

Status

This is a Proposed protocol with a state model on paper. The Prism prototype commits whole segments, but no isolated model or crash test exists yet. Deletes, reader expiry and compaction under pins are undefined below and listed as open.

Definitions and invariants

Each commit gets a log sequence number ℓ. A pin p = (ε, ℓ) names an epoch (seed, dimension, schedule) and a position. The visible set is:

V(p) = { r : lsn(r) ≤ ℓ } # deletes, future work: and del_lsn(r) > ℓ

Legal states of a write

  1. Appended. The record is in the log buffer. Not durable, not visible.
  2. Durable. The log record reached the configured durability boundary. The write may be acknowledged. Still not visible to readers.
  3. Applied. The record is in the in-memory index state. Visible to the writer's own reads only if read-your-writes is chosen; any lag must be explicit.
  4. Sealed. The record is part of an immutable segment. No more changes to that segment.
  5. Published. A snapshot listing the segment becomes current by one pointer swap. From here new readers can pin it.
  6. Retired, then reclaimed. Once compaction replaces the segment and no pin references it, its storage is freed.

A crash at any step must leave a state from which recovery rebuilds exactly the published snapshots the log can justify. That claim is not yet tested at every boundary.

What the Atlas engine already does

The production engine this research sits beside is a separate, more conservative design: a write-ahead log is the single source of truth, the index is derived from it and rebuilt on open, and a poisoned or corrupt state fails closed. Builder-reported and not independently verified:

  • A protected log header; a torn final record is truncated, a corrupt middle record fails the open.
  • Idempotent inserts keyed by operation id, so a retry never applies twice.
  • Tenant scope enforced on every call, with isolation tests.

Power-loss behaviour is not proven: process-kill tests are not power-cut evidence.

Open questions

  • What does a delete mean for a pinned reader, and when is the tombstone reclaimable?
  • What happens to a long-lived or abandoned pin: expire it, and what does the reader see?
  • How much disk can pinned snapshots retain before writers get backpressure?
  • Does an immutable snapshot actually lower tail latency against a carefully controlled mutable-index baseline, once memory retention and write amplification are counted?
  • What is the visibility lag between a durable write and the first snapshot that contains it?

Each of these is on the loophole audit until a test closes it.
