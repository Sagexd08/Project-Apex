The whole note, in one page.

Research Note v1.0 (preprint, not peer reviewed), 2026-10-26. Preliminary synthetic results that have not been reproduced. Numbers are from one machine (benchmarks/prism/results/results.json, source checksum 103fcb801fb94647).

PreprintSynthetic dataUnreproduced

Agentic workloads read and write the same vector store within milliseconds of each other, and other work reports tail latency inflating when inserts run during queries (reported, not reproduced here). We propose Prism, a storage layout for that case. Each vector is rotated by a seeded randomized Hadamard transform and stored once as four nested bit planes, so the quantizer has no trained state and cannot drift as the data changes. A query runs an error-gated cascade: it scores every vector with one bit and reads further planes only for candidates that can still reach the top k.

Readers search immutable snapshots pinned to a write-ahead-log position, so a reader takes no lock after pinning and does not see a partial write (implemented and tested for one writer and four readers). In a Rust reference implementation on synthetic data (20,000 vectors, 256 dimensions, 1,000 queries), a gate width of z = 3 returned the same top 10 as exact search for all 1,000 queries while reading about 1.06 bits per coordinate per vector, against 4 for a flat 4-bit scan; at z = 2 recall@10 was 0.998. This gate is a calibrated heuristic, so the match is an observation, not a guarantee; the only certified bound we tested reads 3.7 to 4.0 bits. Bits read is not total memory, because raw float32 vectors must be kept for the exact rerank.

The saving in bits read was not shown to become a saving in time: with a lookup-table kernel the z = 2 cascade took 0.61 ms per query against 0.55 ms for an optimised exact float scan in the first run, and 0.48 ms against 0.63 ms in a re-run on a busy machine. The time comparison is inconclusive: the sign reversed between runs. On harder synthetic sets it read 1.3 to 1.4 bits at z = 2, and over seven alternating trials a concurrent writer raised median P99 latency by 21% (range 12% to 34%). Open problems: a gate whose provable width does not cost most of the saving, real embedding data, and a kernel that beats an optimised exact scan.
