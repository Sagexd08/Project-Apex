The problem

Where agent memory goes wrong.

An agent that runs for days has to remember earlier work, keep one user’s data apart from another’s, and cope with a request that may or may not have been applied. Most projects write that logic themselves.

Problem 01Storage

Memory spread across systems

Conversation history, records, embeddings and application state live in different places, so finding what an agent needs means querying several of them.

Problem 02Writes

Retried requests

When a network call times out, the caller can’t tell whether the write happened. Sending it again may store it twice.

Problem 03Scope

Who can see what

A similarity search returns the nearest records whether or not this user or task should see them. The restriction has to be added by hand.

Problem 04Debugging

Finding out why

When retrieval returns something unexpected, you need a record of what was written, and when, to work out why.

Project Apex puts the log, scoping and retry handling in the database instead of in application code.

Features

What Project Apex does.

It is an embedded storage engine in Rust, split into four crates: core, storage, index and engine.

001 / Durable writes

A log of every write.

Each record is appended to a write-ahead log with a CRC32 checksum. On startup the log is replayed to rebuild state. If the log is corrupt, opening fails with WAL_CORRUPT instead of skipping records.

002 / Tenant isolation

Each query runs in a scope.

The scope is the caller’s permissions intersected with the key. Tests check that a query never returns another tenant’s records, including when an index panics.

003 / Idempotent writes

A retry is applied once.

A retried write with the same operation id and identical bytes takes effect once. If the outcome of a commit can’t be determined, the caller gets OUTCOME_UNKNOWN instead of a guess.

004 / Swappable index

Exact search today.

Search goes through an AnnIndex trait. The brute-force FlatIndex returns exact results and is the reference any approximate index has to match. No approximate index is wired in yet.

Design

How it is built.

01 / The log comes first

The write-ahead log is the source of truth. The index is rebuilt from it on startup and is never trusted from disk.

02 / Isolation has its own tests

Tenant boundaries are covered by tests for concurrent tenants, a panicking index and replay after a crash.

03 / Numbers come with conditions

Latency, recall, throughput and memory are reported together, with the dataset, hardware and build settings used.

04 / Evidence is tied to a snapshot

Each test result is recorded against a digest of the source. Change a file and the old result no longer counts until it is re-run.

Where it fits

A storage layer, not a framework.

Project Apex stores and retrieves data. It is not a model, an agent framework or a hosted service, so it sits next to whatever you already use.

Try it if

You want a database that logs every write, scopes queries by tenant and applies retries once, and you are happy to read the source and report problems.

Stay with PostgreSQL if

You need relational queries, transactions or a vector index that works today. pgvector covers exact and approximate search.

Stay with your vector database if

You need approximate search at scale now. Project Apex has no approximate index wired in yet.

Status

Early development.

The log, recovery and tenant isolation are implemented and tested. The approximate index, filtered search, macOS support and a capacity policy for the operation map are not done. Do not use it for anything that matters yet.

Questions

Q.001 /What is Project Apex?

An open-source database in Rust for storing and searching the data AI agents produce.

Q.002 /Is it faster than pgvector or Qdrant?

Unknown. No search benchmark has been run.

Q.003 /Can I use it in production?

No. See the status section for what is missing.

Q.004 /Does it do approximate nearest-neighbour search?

Not yet. Search is exact (brute force). An approximate index is planned, and it has to match the exact results before it ships.

Q.005 /What happens on power loss?

Not tested. The durability tests kill the process, which is not the same as losing power.

Q.006 /Which platforms work?

Windows and Linux are tested. macOS is not.

Q.007 /How do I run it?

It is an embedded library that runs inside your own process. There is no server yet.

Q.008 /Why another database?

To find out whether putting the log, tenant scoping and retry handling in the database is simpler than writing them in application code.

Read the source and try to break it.

README / Project Apex

A database for agent memory.

Project Apex writes every change to a write-ahead log and rebuilds its index from that log when it starts. Queries run inside a tenant scope, and a retried write with the same id and the same bytes is applied once.

It is an embedded Rust library. There is no server and no approximate index yet.

Each result belongs to one snapshot.

Test runs, Linux runs and reviews are recorded against a digest of the source. If a file changes, the earlier result is out of date until it is re-run. docs/GATES.md lists what each digest has and hasn’t been checked for.

Killing the process in a test is not the same as losing power, and a missing result is never counted as a pass.

Open items.

The capacity policy for the operation map is unresolved and blocks production use. The approximate index and filtered-search acceptance, macOS testing, a power-loss test and the independent review of the current digest are not done.

There are no speed comparisons with other databases because no search benchmark has been run.
