What we see

An agent does not work like a report. It reads what it knows, acts, writes what it learned, and reads again.

The storage under most agents was designed for the opposite rhythm: load in bulk, build an index, then query for a long time. When the two meet, writes slow reads, tail latency spikes, and a memory that should be instant becomes the part of the loop everyone waits for. We also see that moving bytes is expensive. We have not shown that fewer bytes means less time; see the falsifiers below.

What we believe

Six commitments.

01

Memory should be fast enough to disappear.

An agent should consult everything it knows inside one thought, on a laptop, without a cluster.

02

Nothing to train means no trained state to drift.

A compressor learned from yesterday’s data can be wrong about tomorrow’s. A fixed random rotation has no opinion about the data, and the error scale we gate on is measured and rechecked on shifted data.

03

Pay for precision only when the question needs it.

Most of a corpus is clearly irrelevant to a given query, and one bit is enough to say so. Spend more bits only on the few vectors still in the running.

04

A reader takes no lock and never sees half a write.

Every read happens against a named point in the log: the same question at the same point gives the same answer. Readers still share CPU and memory with writers, and the paper reports that cost.

05

Say what was measured.

Every number carries its data, its machine and the version of the code that produced it. A claim without a measurement is a goal.

06

Keep it open.

The reference implementation, the benchmark and the raw results are public, so anyone can disagree with us with evidence.

What we are building

One stored code. Progressive precision. A snapshot per reader.

Prism: each vector is stored once as nested bit planes, searched by a cascade that reads more planes only for candidates still in contention, and served to readers through snapshots tied to the write-ahead log.

North star

The bar a reader would apply.

A proposed goal, not a claim: an open-source vector database that agents can use as memory. We have no customers and no comparison with any other system. What we can do is write down the bar and try to clear it in public.

Thesis and falsifiers

What would prove us wrong.

Thesis (proposed). Nested bit planes plus log-pinned snapshots can improve the memory, recall and latency trade-off when a store is read while it is written. So far one synthetic benchmark shows bits read falling to about 1.06 per coordinate, and no established time saving over an optimised exact scan (inconclusive: the sign reversed between two runs). We will publish the result either way. A negative result is acceptable. An unsupported positive claim is not.

The saving in bytes read does not become a saving in time on real hardware.
Real embeddings are far less friendly than our synthetic clusters.
The empirical gate misses neighbours more often than its tuning suggests, and a provable gate costs too much to be worth it.
An existing system, such as RaBitQ or TurboQuant combined with a segment design, already gives the same result.
Open by construction

Free to use, and free to inspect.

The core database must not need a paid API, a hosted service, telemetry, or a language model to store, search and recover vectors. The Rust workspace declares Apache-2.0; a top-level licence file, third-party notices and an SBOM are still open. Dependencies are checked with cargo-deny on every verification run. Every number comes from synthetic data with fixed seeds and committed raw results.
